Metrics Reference

SUAVE automatically records mission metrics at the end of each run via the mission_metrics node (suave_metrics package). Results are written as CSV files to a configurable output directory.

Output location

By default results are saved to ~/suave/results/. This can be changed via the result_path ROS parameter or the result_path field in runner_config.yml.

Each run produces a main summary file plus up to three optional per-event files, all using the same base filename (result_filename).

Main summary file — <result_filename>.csv

The metrics node appends a row when it saves mission results. A row does not establish successful completion of a runner attempt. It can remain after recording validation fails or an attempt is superseded by a retry. For runner campaigns, use runs.json to select runs with status: completed and match each CSV row’s run_idx and attempt_id to the current completed attempt. See Inputs and filtering for tool-specific selection rules.

Per-event files

These files are only created if at least one event of the corresponding type occurred. Each has columns: mission_name, datetime, reaction time (s), run_idx, attempt_id (the last two as in the summary file).

<result_filename>_component_recovery_time.csv

One row per thruster failure event. Reaction time is measured from the moment a thruster is reported as failed in /diagnostics to when f_maintain_motion_node transitions back to active (indicating the managing subsystem issued the recovery reconfiguration).

<result_filename>_wv_reaction_time.csv

One row per water visibility change event. Reaction time is measured from the moment the measured water visibility causes a mismatch with the current spiral altitude to when f_generate_search_path_node adopts the correct altitude (via parameter change on /f_generate_search_path_node).

<result_filename>_battery_reaction_time.csv

One row per low battery event. Reaction time is measured from when battery level drops below the threshold (default 0.25) to when generate_recharge_path_node transitions to active.

Notes on mean_reaction_time

The mean reaction time in the summary file averages across all three event types (thruster, water visibility, battery). When comparing managing subsystems, consider inspecting the per-event files to separate performance on each disturbance type.

Live reaction time topic

mission_metrics also publishes mission_metrics/reaction_time (suave_msgs/msg/ReactionTime), one message per adaptation type. adaptation_type is one of the message constants ADAPTATION_THRUSTER (thruster), ADAPTATION_WATER_VISIBILITY (water_visibility), or ADAPTATION_BATTERY (battery). Each message carries the latest reaction time (latest), the running mean (mean), and the number of reactions (count) for that type, in seconds.

At startup, mission_metrics publishes one message per adaptation type with status set to STATUS_INVALID, count 0, and zeroed times. Each recorded reaction then publishes a STATUS_VALID message for the reacting type. Consumers should ignore latest and mean unless status is STATUS_VALID. The publisher uses RELIABLE reliability, TRANSIENT_LOCAL durability, and depth 10, so subscribers must match.

Requirement fulfillment

The suave_requirements package provides the requirement_monitor node, which publishes the runtime fulfillment (std_msgs/Float32 in [0, 1]) of the SUAVE RELAX requirements. It is not started by the default launch files:

ros2 run suave_requirements requirement_monitor

Input

Membership

/requirements/thruster_availability/fulfillment

operational_thrusters on /diagnostics

/requirements/search_footprint/fulfillment

coverage_area on /diagnostics

AS MANY AS POSSIBLE, FuzzyRightShoulder(foot, shoulder)

/requirements/adaptation_reaction_time/<type>/fulfillment

latest of valid mission_metrics/reaction_time messages of that adaptation_type

AS EARLY AS POSSIBLE, FuzzyExponentialDecay(exponent)

/requirements/adaptation_reaction_time/fulfillment

all reaction events

Moving average of the per-event fulfillment over the last reaction_time_window_size events

<type> is thruster, water_visibility, or battery. No fulfillment is published until its input is available: thruster and footprint fulfillment after their first measurement, per-type reaction-time fulfillment after the first STATUS_VALID message of that type, and the combined reaction-time fulfillment after the first valid reaction of any type. STATUS_INVALID messages and unknown adaptation types are ignored (unknown types are logged as warnings). Values are published when inputs change and republished every publishing_period. pipeline_detection stops publishing coverage_area after the first pipeline detection, so the search footprint fulfillment then holds its last value.
